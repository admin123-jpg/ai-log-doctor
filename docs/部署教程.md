## 0. 先理解：这个项目到底在干什么

在动手之前，先建立整体认知。整个系统只做一件事：

> **把日志里的错误，自动变成「人能看懂的排查建议」。**

拆成五步，对应五个代码文件：

| 步骤 | 负责文件 | 输入 → 输出 |
|---|---|---|
| ① 采集日志 | `src/collector.py` | 容器名 → 日志文本 |
| ② 发现异常 | `src/detector.py` | 日志文本 → 「有没有问题 + 问题等级」 |
| ③ 查资料（RAG） | `src/rag.py` | 异常文本 → 知识库里最相关的 3 条运维手册 |
| ④ AI 下结论 | `src/llm.py` | 异常 + 资料 → 根因分析 + 处置建议 |
| ⑤ 存起来、展示 | `src/db.py` + `src/api.py` + `web/index.html` | 结论 → SQLite → 网页 |

**串起这五步的是 `src/pipeline.py`**（pipeline 就是「流水线」的意思）。

你可以先只看 `src/pipeline.py` 里的 `analyze_text()` 函数，它不到 60 行，把整个逻辑写得清清楚楚：

```python
def analyze_text(text, source, service, save=True):
    detection = detect(text)              # ② 检测
    if not detection.hit:
        return None                       # 没异常就结束
    references = kb.retrieve(...)         # ③ RAG 检索
    result = diagnose(...)                # ④ 大模型诊断
    record = {...}                        # ⑤ 组装
    if save:
        record["id"] = db.create_diagnosis(record)
    return record
```

**建议阅读顺序**：`pipeline.py` → `detector.py` → `db.py` → `rag.py` → `llm.py` → `api.py`。

### 2.2 打开项目

**文件 → 打开文件夹** → 选择 `ai-log-doctor` 文件夹。

### 2.3 重要：选择 Python 解释器

这一步新手最容易漏，漏了就会报「找不到模块」。

1. 按 `Ctrl + Shift + P` 打开命令面板
2. 输入 `Python: Select Interpreter`
3. 选择 **`./venv/Scripts/python.exe`**（也就是项目里的虚拟环境）

选完后，VS Code 窗口**右下角**会显示当前解释器。确认它带 `venv` 字样。

### 2.4 打开集成终端

快捷键 `Ctrl + \`` （就是键盘左上角那个反引号），或者菜单「终端 → 新建终端」。

终端打开后，确认前面有 `(venv)` 前缀，像这样：
```
(venv) PS C:\...\ai-log-doctor>
```

如果没有，手动激活：
```powershell
# PowerShell
venv\Scripts\Activate.ps1

# 如果提示「禁止运行脚本」，先执行一次：
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

> **Git Bash 用户**（如果你把 VS Code 默认终端设成了 bash）：
> ```bash
> source venv/Scripts/activate
> ```

### 2.5 中文乱码问题（Windows 常见）

如果终端里中文显示为乱码，在终端执行：
```powershell
chcp 65001
```
或者设置环境变量后重启终端：
```powershell
$env:PYTHONIOENCODING="utf-8"
```

**验证**：终端里执行 `python -c "print('中文测试')"`，应该正常显示中文。

## 3. 获取项目并创建虚拟环境

### 3.1 虚拟环境是什么？为什么必须用它？

**虚拟环境 = 给这个项目单独准备的 Python 运行环境。**

好处：
- 装依赖不会污染系统 Python
- 项目 A 用 Flask 2.0，项目 B 用 Flask 3.0，互不干扰
- 面试时说「我会用 venv 管理依赖」是基础加分项

### 3.2 创建

在 VS Code 终端里（确保当前目录是 `ai-log-doctor`）：

```bash
# 创建虚拟环境（文件夹名叫 venv，这是约定俗成的名字）
python -m venv venv

# 激活（PowerShell / CMD）
venv\Scripts\activate

# Git Bash 用户用这条
source venv/Scripts/activate
```

**验证**：激活后命令行前面出现 `(venv)`。

## 4. 安装依赖（以及每个依赖是什么）

### 4.1 一键安装

```bash
pip install -r requirements.txt
```

> 如果下载慢，用国内镜像（清华源）：
> ```bash
> pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
> ```

### 4.2 每个依赖到底是什么（面试会问）

| 依赖 | 一句话解释 | 在这个项目里干什么 |
|---|---|---|
| **FastAPI** | 用 Python 写接口的现代框架 | 提供所有 HTTP 接口，并自动生成 `/docs` 文档 |
| **Uvicorn** | ASGI 服务器 | FastAPI 写的应用不能直接跑，要靠 Uvicorn 启动、监听端口、处理并发请求 |
| **Pydantic** | 数据校验库 | 定义接口「接收什么参数、返回什么结构」，传错了自动返回 422 错误 |
| **Requests** | HTTP 客户端库 | 调用大模型 API 和 Embedding API |
| **python-dotenv** | 读取 `.env` 文件 | 把 API Key 从代码里隔离出来，避免上传到 GitHub 泄露 |
| **SQLite** | 轻量级数据库（Python 自带） | 存诊断记录，数据库就是 `data/doctor.db` 一个文件 |
| **Chroma** | 向量数据库（**可选**） | 存知识库片段的向量，做相似度检索。**装不上会自动降级** |
| **pytest** | 测试框架 | 跑单元测试，验证代码没写错 |

### 4.3 如果 chromadb 装不上

这是**很常见**的情况（它需要编译，Windows 上容易失败）。

**解决办法：不用管。** 直接跳过它：

```bash
# 只装核心依赖
pip install fastapi uvicorn requests python-dotenv pydantic pytest
```

程序检测到没有 chromadb，会自动使用**内置的内存向量库**（纯 Python 实现的余弦相似度算法），功能完全正常。

你可以在 `src/rag.py` 里看到这个降级逻辑（`_chroma_available()` 和 `KnowledgeBase.__init__`）。

**验证**：
```bash
pip list
```
应该能看到 fastapi、uvicorn、requests、dotenv、pydantic、pytest。

## 5. 配置文件 .env

### 5.1 创建

```bash
# Windows PowerShell
copy .env.example .env

# Git Bash / Linux
cp .env.example .env
```

### 5.2 现在要不要填 API Key？

**先不要。** 保持默认即可，程序会进入 **Mock 模式**：

- Mock 模式 = 用内置规则库匹配日志，生成诊断结论
- 好处：不需要花钱、不需要等申请，**整条链路立刻能跑通**
- 等你跑通全流程、看到效果了，再回来填 Key（见第 15 节）

### 5.3 关键配置项说明

```ini
# 留空 = Mock 模式
LLM_API_KEY=

# 要监控哪些容器（名字要和 docker-compose.yml 里的服务名一致）
WATCH_CONTAINERS=demo-nginx,demo-app,demo-mysql

# 向量库后端：auto（自动）/ chroma / simple
# 新手建议先改成 simple，排除干扰
VECTOR_BACKEND=auto

# 服务端口
API_PORT=8000
```

> ⚠️ `.env` 已经在 `.gitignore` 里，**不会被提交到 GitHub**。这是防止密钥泄露的标准做法，面试时可以说出来。

## 7. 第二步：构建 RAG 知识库

```bash
python -m src.main kb
```

**这一步发生了什么**（对应 `src/rag.py`）：

1. 读取 `knowledge/` 下所有 `.md` 文件
2. 按 `##` 二级标题切成 30 个片段（每个片段 = 一个错误类型的完整说明）
3. 每个片段转成向量（数字数组）
4. 存进向量库，并缓存到 `data/kb_memory.json`

**同时它会演示两次检索**，让你直观看到 RAG 的效果：

```
--- 检索效果演示 ---

查询：Connection refused
  [1] docker-errors.md · 容器间 Connection refused 无法访问  （相似度 0.0723）
  [2] nginx-errors.md · 502 Bad Gateway  （相似度 0.0493）

查询：磁盘空间不足
  [1] docker-errors.md · No space left on device 磁盘空间不足  （相似度 0.2779）
  [2] mysql-errors.md · No space left on device 磁盘满  （相似度 0.2154）
```

**✅ 验证标准**：片段数是 30，检索结果和问题相关。

> 💡 **这就是 RAG 的核心价值**：不是让 AI 凭空编，而是先从你的运维手册里找到相关资料，把资料一起交给 AI。
> 你会看到最终诊断结果里带有「参考来源」，那就是这里检索出来的。

**自定义测试**（换成你关心的问题）：

## 8.5 加餐：分析真实中间件日志（Redis / MySQL / Tomcat / Nginx / ES）

前面用的是 Docker 容器日志。但实际工作中，更常见的场景是**别人丢给你一堆日志文件让你分析**。
项目自带了 5 个中间件的日志，可以直接离线分析，不需要启动任何服务。

### 日志文件在哪

`samples/app-logs/` 目录：

| 文件 | 里面埋了哪些问题 |
|---|---|
| `redis.log` | RDB 持久化失败（MISCONF）、fork 内存不足、maxmemory 淘汰、主从断开、maxclients |
| `mysql-error.log` | 慢查询、Too many connections、死锁、磁盘满、主从复制报错 |
| `tomcat-catalina.out` | 空指针异常、数据库连接池耗尽、Too many open files、Java heap space OOM |
| `nginx-error.log` | 502、504、no live upstreams、磁盘满、SSL 握手失败、限流 |
| `elasticsearch.log` | 磁盘水位只读、内存熔断、GC 频繁、分片分配失败、主节点选举失败 |

### 一条命令分析

```bash
python -m src.main ingest --clear
```

| 参数 | 作用 |
|---|---|
| `--clear` | 分析前先清空旧记录（只想看这批日志的结果时用它） |
| `--dry-run` | 只分析不入库，先看看效果 |
| `--dir <路径>` | 分析你自己的日志目录，默认是 `samples/app-logs` |

### 输出什么样

```
【redis】共 33 行，切出 4 个异常片段
  ── 片段 1 [HIGH] 命中「Failed」
     根因：Redis 的 RDB 持久化失败（目录无写权限或磁盘满），按 stop-writes-on-bgsave-error...
     RAG：redis-errors.md · MISCONF Redis RDB 持久化失败导致写入被禁 （相似度 0.2855）
  ── 片段 4 [HIGH] 命中「ERROR」
     根因：Redis 主从复制断开，或客户端连接数达到 maxclients 上限。...
     RAG：redis-errors.md · 主从复制断开 Connection with master lost （相似度 0.0985）

汇总：5 个日志文件 → 22 个异常片段 → 生成 21 条诊断记录
```

**✅ 验证标准**：每个文件切出 2 个以上片段，且 RAG 参考来源指向对应的
`redis-errors.md` / `tomcat-errors.md` / `middleware-errors.md` 等手册。

> ⚠️ 改了 `knowledge/` 下的文档后，记得重建知识库：`python -m src.main kb --force`

### 这里有两个技术点值得搞懂（面试能聊）

**① 一个日志文件要切出多个问题，而不是只诊断第一个**

最初我按「行间隔」合并异常行，结果 redis.log 里 5 个不同的错误被合并成一大段，
最终只诊断出第一个问题。后来改成**按错误模式切分**：拿已知错误模式去日志里逐个匹配，
每种模式取一段上下文，段与段不重叠。片段数从 8 个提升到 22 个。

**② 规则的顺序会影响判断结果**

`OutOfMemoryError` 这个字符串里恰好含有 `MemoryError`。
如果通用的「容器 OOMKilled」规则排在前面，JVM 堆溢出就会被误判成「容器被 OOM 杀掉」。
所以具体规则（Java heap space）必须排在泛化规则之前 ——
这是写规则引擎时很典型的坑。

> 💡 真实生产系统里这类问题叫「日志事件聚类」，
> ELK 用 fingerprint 指纹、Drain 等算法处理。可以作为项目的后续扩展方向。

### 换成你自己的日志

把任意 `.log` / `.out` / `.txt` 文件丢进 `samples/app-logs/`，再跑一次 `ingest` 即可。
程序会根据**文件名自动判断是哪种中间件**（匹配 redis/mysql/tomcat/nginx/elasticsearch 等关键词），
比如 `redis-cluster-01.log` → 服务名 `redis`；认不出来就用文件名本身当服务名。

## 10. 重点：用 FastAPI /docs 做 CRUD 实操

这是你要求的重点，我详细讲。

### 10.1 打开文档

### 10.2 完整 CRUD 实操

> CRUD = **C**reate（增）、**R**ead（查）、**U**pdate（改）、**D**elete（删）

#### 🔵 C - 创建：提交一段日志触发诊断

1. 找到绿色的 `POST /api/diagnoses`，点开
2. 点 **Try it out**
3. Request body 里会自动出现示例，改成下面这段（换成任意错误日志都行）：

```json
{
  "raw_log": "pymysql.err.OperationalError: (2003, \"Can't connect to MySQL server on 'demo-mysql' ([Errno 111] Connection refused)\")",
  "source": "manual",
  "service": "my-test-service"
}
```

4. 点 **Execute**
5. 往下看 **Response body**，你会看到：

```json
{
  "code": 0,
  "message": "诊断完成",
  "data": {
    "id": 35,
    "service": "my-test-service",
    "severity": "high",
    "matched_keyword": "Error",
    "root_cause": "目标服务未启动或网络不通，导致连接被拒绝...",
    "suggestions": [
      "执行 docker ps -a 确认目标容器状态是否为 Up",
      "执行 docker network inspect 确认两个容器在同一个网络",
      "..."
    ],
    "used_references": [
      {
        "source": "docker-errors.md",
        "title": "容器间 Connection refused 无法访问",
        "score": 0.2353
      }
    ]
  }
}
```

**重点看这三个字段**：
- `root_cause`：AI（或规则库）给的根因分析
- `suggestions`：具体的排查建议
- `used_references`：**RAG 检索到的参考资料及其相似度** —— 这就是 RAG 工作的证据

> 💡 记住返回的 `id`（这里是 35），后面查、改、删都要用它。

#### 🔵 R - 查询列表

1. 找到 `GET /api/diagnoses`，点 **Try it out**
2. 参数说明：
   - `limit`：每页几条，填 `10`
   - `offset`：跳过几条（翻页用），填 `0`
   - `service`：按服务名筛选，如 `demo-app`（留空则不过滤）
   - `status`：`new` / `resolved` / `ignored`
   - `severity`：`high` / `medium` / `low`
   - `keyword`：在日志里模糊搜索
3. 点 **Execute**，看返回的 `items` 数组

#### 🔵 R - 查询单条

1. 找到 `GET /api/diagnoses/{did}`，点 **Try it out**
2. `did` 填刚才的 `35`
3. **Execute**

#### 🔵 U - 更新：标记为已解决

1. 找到 `PUT /api/diagnoses/{did}`，点 **Try it out**
2. `did` 填 `35`
3. Request body 填：
```json
{
  "status": "resolved"
}
```
4. **Execute** → 返回更新后的完整记录，`status` 变成 `resolved`

> 想看参数校验生效：把 `status` 改成 `"abc"` 再执行，会返回 400 错误，提示「status 只能是 [...] 之一」。这就是 Pydantic + 手写校验在起作用。

#### 🔵 D - 删除

1. 找到 `DELETE /api/diagnoses/{did}`，`did` 填 `35`
2. **Execute** → 返回「记录 35 已删除」
3. 再用 `GET /api/diagnoses/{did}` 查一次，会返回 **404**，证明真的删了

## 13. 项目打包：构建并运行 Docker 镜像

### 13.1 打包流程

```bash
# 1. 构建镜像（注意最后的点，表示当前目录）
docker build -t ai-log-doctor:latest .

# 2. 查看镜像
docker images | findstr ai-log-doctor

# 3. 运行容器
docker run -d --name ai-doctor -p 8000:8000 ai-log-doctor:latest

# 4. 看日志
docker logs -f ai-doctor

# 5. 停止并删除
docker stop ai-doctor
docker rm ai-doctor
```

### 13.2 Dockerfile 逐行讲解

打开项目根目录的 `Dockerfile`，关键几行：

```dockerfile
FROM python:3.11-slim          # 基础镜像：装好 Python 3.11 的精简 Linux
WORKDIR /app                   # 容器内工作目录
ENV PYTHONUNBUFFERED=1 ...     # 日志不缓冲，否则 docker logs 看不到实时输出

COPY requirements.txt .        # 先只复制依赖文件
RUN pip install -r requirements.txt   # 装依赖（这一层会被缓存）
COPY . .                       # 再复制代码

EXPOSE 8000                    # 声明端口
HEALTHCHECK ...                # 健康检查，容器编排靠它判断存活
CMD ["python","-m","src.main","serve","--host","0.0.0.0"]
```

> 💡 **为什么要先 COPY requirements.txt 再 COPY 代码？**
> 利用 Docker 的**层缓存**：依赖没变时，改代码重新构建不会重新 `pip install`，速度从几分钟变成几秒。
> 这是面试常问的 Dockerfile 优化点。

> ⚠️ **注意 `--host 0.0.0.0`**：容器里必须监听 `0.0.0.0` 才能从外部访问。
> 如果写 `127.0.0.1`，只有容器内部能访问，宿主机打不开 —— 这是新手最常踩的坑。

### 13.3 打包时排除了什么（.dockerignore）

```
venv/          # 虚拟环境不进镜像（镜像里会重新装）
__pycache__/   # Python 缓存
.env           # 密钥绝对不能进镜像
data/          # 运行时数据
.git/          # Git 历史
docs/          # 文档
```

## 17. 故障排查表

| 现象 | 原因 | 解决办法 |
|---|---|---|
| `python` 不是内部或外部命令 | 装 Python 时没勾 Add to PATH | 重装 Python，勾选该项；或手动添加环境变量 |
| 终端没有 `(venv)` 前缀 | 虚拟环境没激活 | 执行 `venv\Scripts\activate` |
| PowerShell 提示「禁止运行脚本」 | 执行策略限制 | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| `ModuleNotFoundError: No module named 'fastapi'` | 解释器选错了 | VS Code 里 `Ctrl+Shift+P` → `Python: Select Interpreter` → 选 `./venv` |
| 中文乱码 | 终端编码 | `chcp 65001`，或设 `PYTHONIOENCODING=utf-8` |
| `pip install chromadb` 失败 | 需要编译 | 不用管，程序会自动降级；或从 requirements.txt 注释掉 |
| 端口 8000 被占用 | 其他程序占用 | 改 `.env` 里 `API_PORT=8001`；或 `netstat -ano | findstr :8000` 查杀 |
| 服务启动了但打不开 /docs | 服务没起来或地址错 | 看终端日志；确认访问 `127.0.0.1` 不是 `0.0.0.0` |
| 提交日志返回 400「未检测到异常关键字」 | 日志里没有错误关键字 | 换一段含 ERROR / Exception / Timeout 的日志 |
| 知识库片段数为 0 | knowledge 目录为空或路径错 | 确认 `knowledge/*.md` 存在 |
| 改了知识库文档但检索没变 | 向量库缓存未更新 | `python -m src.main kb --force` 或调 `POST /api/kb/rebuild` |
| Docker 命令不存在 | Docker 没装/没启动 | 装 Docker Desktop 并等状态变为 Running |
| `docker compose` 报错 | 旧版命令是 `docker-compose` | 用新版 `docker compose`（中间是空格） |
| 容器内服务访问不了 | 监听地址写成了 127.0.0.1 | 改成 `0.0.0.0` |

### 18.2 面试话术参考

**介绍项目（30 秒版）**：

> “我做了个叫 AI 容器日志医生的项目。它自动采集 Docker 容器和 CI 流水线的日志，
> 用关键字和正则检测异常，然后通过 RAG 从我自己整理的运维知识库里检索相关资料，
> 再把日志和资料一起交给大模型，生成根因分析和处置建议，最后存进 SQLite 并在 Web 面板上展示。
> 整个项目用 GitHub Actions 做 CI，会自动跑测试和构建镜像。
> 比较特别的一点是，流水线失败时它会自己抓日志做 AI 诊断，把结论评论到 PR 上。”

**被问「数据来源」**：

> “日志有三个来源：真实容器日志、我手写的故障样本、模拟的 CI 失败日志。
> 知识库是我整理的运维排错手册，按错误类型分成 30 个片段。
> 数据库里的记录是系统真实跑出来的——种子脚本会走完整流程生成历史数据，
> 不是为了演示硬编码的假 JSON。”

**被问「RAG 怎么实现的」**：

> “知识库按 Markdown 二级标题切片，然后向量化存进向量库。
> 检索时把异常日志也向量化，算余弦相似度取 Top-3。
> 我做了降级设计：装了 Chroma 就用生产级向量库，装不上就用纯 Python 实现的内存检索，
> 没配 API Key 就用本地算法做向量化。这样保证任何环境都能跑通。”

**被问「遇到什么难点」**：

> “主要是两个。一是新手环境容易卡住，所以我做了自动降级；
> 二是 RAG 的切片策略——一开始按固定字数切，会把一个错误类型的说明切断，
> 检索出来上下文不完整，后来改成按 Markdown 二级标题切，效果好很多。”
