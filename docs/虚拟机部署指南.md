> **这份文档记录什么**
> 把 AI 容器日志医生部署到 **无外网** 的 CentOS 7 虚拟机上，并从 Windows 本机浏览器访问的完整过程。

## 二、目标机器的三个硬约束

部署前探测到的环境，**这三点决定了整个方案**：

### 约束 1：完全没有 Python

```
$ python3 -V
bash: python3: 未找到命令
```

CentOS 7 的 yum 源里最高只有 Python 3.6.8，而项目依赖 FastAPI 0.115 + Pydantic 2.x，**必须 3.8+**。

### 约束 2：没有外网

```
$ curl -sI https://pypi.tuna.tsinghua.edu.cn/simple/
（超时，返回码 000）

$ bash -c 'cat < /dev/null > /dev/tcp/pypi.tuna.tsinghua.edu.cn/443'
bash: connect: 网络不可达
```

HTTP / HTTPS 全部不通，TCP 层直接「网络不可达」。

> ⚠️ **一个容易误判的点**：`yum repolist` 能显示 30899 个包，看起来像有网 ——
> 但它读的是 **`/var/cache/yum` 里的本地缓存元数据**，实际下载时照样失败。
> **判断有没有外网，要用 `curl` 实测，不要信 `yum repolist`。**

### 约束 3：系统库太老

| 组件 | 版本 | 影响 |
|---|---|---|
| glibc | 2.17 | 新版软件常要求 2.28+ |
| OpenSSL | 1.0.2k | Python 3.10+ **编译时**要求 1.1.1+ |
| gcc | **未安装** | 无法源码编译 Python（且 yum 装不了） |

**结论：既不能在线 pip 安装，也不能源码编译。**

## 三、架构：为什么是「上传独立 Python」

既然不能装、不能编译，答案是：**从本机上传一个免安装的 Python 运行环境**。

### 技术选型过程

| 方案 | 可行性 | 结论 |
|---|---|---|
| `yum install python3` | yum 无外网，且版本只有 3.6 | ❌ |
| 源码编译 Python 3.11 | 需要 gcc + OpenSSL 1.1.1+，两个都缺 | ❌ |
| Miniconda | 可用，但安装包 ~140MB，装完 ~700MB，磁盘紧张 | ⚠️ 备选 |
| **python-build-standalone** | **28MB 压缩包，解压即用，自带 OpenSSL/SQLite** | ✅ **采用** |

**选用 `python-build-standalone`**（Astral 维护的免编译 Python 发行版）：

- 自带 OpenSSL 3.0.13、SQLite 3.45.1 —— **完全不依赖系统库**，绕开 glibc/OpenSSL 问题
- 选 **3.11.9**（构建于 2024-04，在 CentOS 7 停更前，兼容性最好）
- 压缩包仅 28MB，解压后 106MB

### 依赖怎么办：离线 wheelhouse

包也不能在线装，所以：**在本机下载好 Linux 专用 wheel → 上传 → 离线安装**。

```bash
# 在本机（Windows）执行：下载目标平台专用的 wheel
pip download -d wheels \
  --only-binary=:all: \
  --platform manylinux2014_x86_64 \    # 目标平台标签
  --python-version 311 \
  --implementation cp \
  --abi cp311 \
  -r requirements-vm.txt
```

> `manylinux2014` = glibc 2.17 基线，**正好对应 CentOS 7**。
> 共 16 个 wheel、3.7MB，其中 `pydantic_core` 和 `charset_normalizer` 是 Linux 原生编译包，
> 必须用这个标签下载，否则装不上。

### 整体数据流

```
   Windows 本机                          CentOS 7 虚拟机
┌──────────────────┐              ┌──────────────────────────┐
│ 1. 打包项目       │              │ /opt/logs                │
│ 2. 下载独立 Python│ ──SFTP──→    │   ├─ mysql-error.log     │ 真实日志
│ 3. pip download   │  (~32MB)     │   ├─ systemd-error.log   │
│    Linux wheel    │              │   └─ docker-*.log        │
└──────────────────┘              │        ↓ ingest          │
                                  │ /opt/ai-log-doctor       │
                                  │   ├─ venv (离线装好)      │
                                  │   └─ data/doctor.db      │
                                  │        ↓ systemd          │
   浏览器访问 ←──────── HTTP ──────│  0.0.0.0:8000            │
http://192.168.136.188:8000/      └──────────────────────────┘
```

**Windows 端什么都不用装** —— 前端用的是相对路径（`fetch('/api/health')`），
浏览器打开哪个 IP，它就去哪个 IP 取数据，**零改动**。

## 四、完整部署步骤（可复现）

### 阶段 A：在 Windows 本机准备上传物

```bash
cd C:/Users/ss/WorkBuddy/2026-09-15-00-46-43

# A1. 打包项目（排除 venv / data / 缓存）
tar -czf ai-log-doctor.tar.gz \
  --exclude='ai-log-doctor/venv' \
  --exclude='ai-log-doctor/data' \
  --exclude='ai-log-doctor/.pytest_cache' \
  --exclude='*/__pycache__' --exclude='*.pyc' \
  ai-log-doctor
# → 127KB，44 个文件

# A2. 下载独立 Python（3.11.9，Linux x86_64，免编译）
#     源：南大 GitHub Release 镜像（GitHub 直连不通）
#     https://mirror.nju.edu.cn/github-release/astral-sh/python-build-standalone/20240415/
#     cpython-3.11.9%2B20240415-x86_64-unknown-linux-gnu-install_only.tar.gz
# → 28.4MB

# A3. 创建 VM 版依赖清单（不含 chromadb / pytest，省磁盘）
cat > requirements-vm.txt <<'EOF'
fastapi==0.115.0
uvicorn==0.30.6
requests==2.32.3
python-dotenv==1.0.1
pydantic==2.9.2
EOF

# A4. 下载 Linux 专用 wheel
pip download -d wheels --only-binary=:all: \
  --platform manylinux2014_x86_64 --python-version 311 \
  --implementation cp --abi cp311 -r requirements-vm.txt \
  -i https://pypi.tuna.tsinghua.edu.cn/simple
# → 16 个 wheel，3.7MB
```

### 阶段 B：上传（SFTP，共约 32MB）

```python
# 用 paramiko 上传到 /root/deploy-stage/
# 也可以直接用 scp：
scp python311-linux.tar.gz ai-log-doctor.tar.gz root@192.168.136.188:/root/deploy-stage/
scp -r wheels root@192.168.136.188:/root/deploy-stage/
```

### 阶段 C：在虚拟机上安装

```bash
# C1. 部署 Python（解压即用，无需编译）
mkdir -p /opt/python311
tar -xzf /root/deploy-stage/python311-linux.tar.gz -C /opt/python311 --strip-components=1
/opt/python311/bin/python3.11 -V     # → Python 3.11.9

# C2. 部署项目
mkdir -p /opt/ai-log-doctor
tar -xzf /root/deploy-stage/ai-log-doctor.tar.gz -C /opt/ai-log-doctor --strip-components=1

# C3. 创建虚拟环境
cd /opt/ai-log-doctor
/opt/python311/bin/python3.11 -m venv venv

# C4. 离线安装依赖（--no-index 表示不联网）
venv/bin/pip install --no-index --find-links /root/deploy-stage/wheels \
  fastapi==0.115.0 uvicorn==0.30.6 requests==2.32.3 python-dotenv==1.0.1 pydantic==2.9.2

# C5. 配置：必须监听 0.0.0.0，否则 Windows 访问不到
cp .env.example .env
sed -i 's/^API_HOST=.*/API_HOST=0.0.0.0/' .env

# C6. 环境自检 + 建知识库
venv/bin/python -m src.main check
venv/bin/python -m src.main kb
```

### 阶段 D：配置 systemd 服务

```ini
# /etc/systemd/system/ai-log-doctor.service
[Unit]
Description=AI Log Doctor - 日志 AI 诊断服务
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/ai-log-doctor
Environment=PYTHONIOENCODING=utf-8
ExecStart=/opt/ai-log-doctor/venv/bin/python -m src.main serve --host 0.0.0.0 --port 8000
Restart=always          # 崩溃自动重启
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable ai-log-doctor      # 开机自启
systemctl start  ai-log-doctor
systemctl status ai-log-doctor      # 确认 active (running)
```

### 阶段 E：采集日志并分析

```bash
bash /opt/ai-log-doctor/scripts/collect-vm-logs.sh 600
cd /opt/ai-log-doctor && venv/bin/python -m src.main ingest --dir /opt/logs --clear
```

### 阶段 F：Windows 验证

浏览器打开 **http://192.168.136.188:8000/** —— 完成。

## 五、日常维护命令

### 5.1 最常用：`exec.sh`（推荐）

项目根目录下有一个管理脚本，**启动/停止/重启一条命令搞定**：

```bash
cd /opt/ai-log-doctor

sh exec.sh start      # 启动（等健康检查通过才返回）
sh exec.sh stop       # 停止
sh exec.sh restart    # 重启
sh exec.sh status     # 查看状态 + 接口健康检查
sh exec.sh logs       # 实时看日志
sh exec.sh backup     # 备份数据库（生成演示数据前务必执行）
```

输出示例：

```
$ sh exec.sh status
=========== ai-log-doctor 状态 ===========
管理方式    : systemd
运行状态    : active
开机自启    : enabled
监听地址    : 0.0.0.0:8000
Python      : Python 3.11.9
健康检查    : HTTP 200 ✓ 服务正常
==========================================
```

**它的一个贴心设计**：脚本会先检测机器上有没有 systemd 服务单元 ——
有就走 `systemctl`（享受开机自启与崩溃自动重启），
没有就自动降级为 `nohup` + PID 文件的方式管理。
**两条路径的命令完全一样**，所以同一份脚本在服务器、容器、WSL 里都能用。

### 5.2 直接用 systemctl（需要更细的控制时）

```bash
systemctl status  ai-log-doctor          # 看状态
systemctl restart ai-log-doctor          # 重启
systemctl stop    ai-log-doctor          # 停止
journalctl -u ai-log-doctor -f           # 实时看日志
journalctl -u ai-log-doctor -n 100       # 看最近 100 行
```

### 5.3 业务操作

```bash
cd /opt/ai-log-doctor

bash scripts/collect-vm-logs.sh 600                    # 采集真实日志
venv/bin/python -m src.main ingest --dir /opt/logs     # 分析日志
venv/bin/python -m src.main kb --force                 # 改了 knowledge/*.md 后重建知识库
venv/bin/python -m src.main check                      # 环境自检

# 直接查数据库
sqlite3 data/doctor.db "SELECT id,service,severity,matched_keyword FROM diagnoses LIMIT 10;"

# 清理上传残留（省 29MB）
rm -rf /root/deploy-stage
```

### 5.4 ⚠️ 一条必须记住的红线

**不要随意点前端页面上的「生成演示数据」按钮。**

它调用 `/api/seed`，而该接口默认带 `clear=true` ——
**会先清空整张 `diagnoses` 表**，包括从真实日志分析出来的记录，且无法恢复。

> 这个坑真实发生过：误点一次，33 条真实分析记录全没了。

**已实施的防护**：

1. 前端按钮加了**二次确认弹窗**，明确警告会清空全部记录
2. 接口返回值如实报告清空了多少条（`cleared: 33`）
3. `exec.sh backup` 提供一键备份

**操作前先备份**：

```bash
sh exec.sh backup
# → 已备份到：/opt/ai-log-doctor/data/doctor.db.bak-20260917-150810
```

## 六、日志数据来源

### 结论：用这台虚拟机上**真实运行的日志**，比我手写的样本强得多

| 来源 | 路径 | 真实性 | 建议 |
|---|---|---|---|
| **MySQL 错误日志** | `/var/log/mysqld.log`（24MB） | ⭐⭐⭐ 真实生产日志 | **首选** |
| systemd 系统日志 | `journalctl -p err` | ⭐⭐⭐ 真实 | 建议（要按级别过滤） |
| **Docker 容器日志** | `docker logs <容器>` | ⭐⭐⭐ 真实 | 首选（Harbor 容器在跑） |
| 内核日志 | `dmesg` | ⭐⭐ 真实但噪音大 | 可选 |
| 手写样本 | `samples/app-logs/` | ⭐ 假数据 | 仅用于首次演示 |

### 采集脚本：`/opt/ai-log-doctor/scripts/collect-vm-logs.sh`

```bash
bash /opt/ai-log-doctor/scripts/collect-vm-logs.sh 600    # 参数=每个文件取多少行
```

它做了 5 件事（**关键在「过滤」**）：

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 1 | MySQL 只取 `[ERROR]` / `[Warning]` 行 | 全文 2 万多行噪音太多 |
| 2 | `journalctl -p err` 只取 err 及以上 | 避免正常启动日志被误判 |
| 3 | 遍历运行中的容器取最近 300 行 | 真实的容器日志 |
| 4 | `dmesg` 最近 300 行 + `boot.log` | 内核与启动异常 |
| 5 | 扫描 nginx / redis / tomcat 日志目录 | 若以后装了这些中间件 |

**实测采集结果**：

```
mysql-error.log              64K
systemd-error.log           468B
docker-harbor-jobservice.log 35K
docker-registryctl.log       22K
kernel-dmesg.log             22K
```

## 七、真实日志暴露的三个问题

**这部分最有价值** —— 换成真实数据后，系统立刻暴露了在假样本上看不到的缺陷。

### 问题 1：真实日志的常态是「同一个故障重复几千次」

对真实 MySQL 日志做归一化统计（去掉时间戳和数字）：

```
     67  [ERROR] Do you already have another mysqld server running on port: N ?
     67  [ERROR] Aborting
     66  [ERROR] Can't start server: Bind on TCP/IP port: Address already in use
```

**200 行 ERROR，其实只有 1 个故障**：MySQL 启动时 3306 端口被占用，反复重试了 67 次。

系统的表现：切出 33 个片段 → 生成 **33 条几乎一样的记录**。

> **正确的展示应该是**：1 个故障 + 出现次数 67，而不是 33 条独立记录。

### 问题 2：单纯的 MD5 去重**不够用**

这一点很反直觉，我实测验证过：

```
总记录数：81
去重后（按 raw_log 原文哈希）：81
重复率：0.0%    ← 看起来没有重复！
```

**为什么？因为每行的「时间戳」都不一样。** 原文哈希算出来全都不同，但内容语义完全一样。

> **正确做法是「归一化指纹」**：先剥掉时间戳、数字、IP 等易变部分，再对剩下的「模板」做哈希。
> 这正是 ELK 里 **fingerprint** 处理器做的事 —— 也是日志聚类（Drain 算法）的入门形态。

### 问题 3：上下文截取会「污染」结论

系统的 `extract_context()` 会取关键字**前 2 行、后 3 行**。在真实密集日志里，这会把**相邻但不相关**的错误行卷进同一个片段：

```
2026-09-03T07:45:59 [Warning] CA certificate ca.pem is self signed.     ← 被诊断为 HIGH
2026-09-03T07:45:59 [ERROR] Can't start server: Bind on TCP/IP port... ← 真正的错误
```

结果：78 条 TLS 警告记录，全部被判成 **HIGH** 严重度，根因写的是「端口被占用」。

**根因**：`judge_severity()` 判断的是整个 snippet 而不是那一行；片段里混进了 `Address already in use`，命中了端口冲突规则。

> **改进方向**：严重度按**命中的那一行**判断，而不是整个上下文片段。

### 这三个问题说明什么

**假数据永远暴露不出真问题。** 我的 `samples/app-logs/` 是精心设计的「每个错误独立成段」，
所以在假数据上切分效果很好（22 片段 / 21 条）；一到真实日志就现原形。

**这恰恰是这次部署最大的收获** —— 也是一段很有说服力的真实经历：

> 「我用虚拟机上的真实 MySQL 日志替换了手写样本，结果发现系统的三个缺陷：
> 第一，真实日志里同一个故障会重复几千次，我的系统生成了 33 条重复记录；
> 第二，我原计划用 MD5 去重，但实测发现**时间戳不同导致哈希全都不同**，
> 正确做法是 ELK 那种归一化指纹；
> 第三，密集日志里我的上下文截取会把不相关的错误行卷进来，导致严重度误判。」

## 八、踩坑记录

| 坑 | 现象 | 原因 | 解决 |
|---|---|---|---|
| **以为有外网** | `yum repolist` 显示 30899 个包 | 读的是本地缓存元数据 | 用 `curl` / TCP 实测才有结论 |
| **GitHub 不可达** | 下载独立 Python 超时 | 国内网络 | 用南大 GitHub Release 镜像 |
| **下载中途断连** | `ConnectionResetError`，只下了 5MB | 长连接被重置 | 写**断点续传**下载器（Range + 重试 20 次） |
| **CentOS 7 装不了高版本 Python** | yum 只有 3.6；编译缺 gcc+OpenSSL1.1.1 | 系统太老 | 用免编译的独立 Python |
| **Windows 访问不到** | `curl 127.0.0.1` 正常，跨机不通 | 默认监听 `127.0.0.1` | 改 `API_HOST=0.0.0.0` |

## 十、后续补充：有网之后的标准配置（含三个缺陷修复）

部署完成一段时间后虚拟机恢复外网，于是把之前因为「无网」而做的妥协全部补回来，
并修掉了三个真实缺陷。

### 10.1 网络修复：不是网关问题，是 IPv6 优先

**现象**：`curl` 访问任何外网都失败，pip 报 `[Errno 101] 网络不可达`。

**排查过程**：

| 测试 | 结果 | 结论 |
|---|---|---|
| `ping 192.168.136.2`（网关） | ✅ 通，0.2ms | 网关正常 |
| `ip route` | ✅ `default via 192.168.136.2 dev ens33` | 路由正常 |
| `curl -4 https://pypi.tuna.tsinghua.edu.cn` | ✅ **HTTP 200** | **IPv4 外网其实是通的！** |
| `curl -6 ...` | ❌ 000 | IPv6 不通 |
| `ip -6 route` | 只有 `unreachable` 条目 | **没有 IPv6 路由** |

**根因**：DNS 同时返回 A（IPv4）和 AAAA（IPv6）记录，glibc 默认按 RFC 3484
**优先选择 IPv6**，而虚拟机没有 IPv6 路由 → 连接直接失败。
CentOS 7 里 `/etc/gai.conf` 默认不存在，所以用的是「IPv6 优先」的默认排序。

**修复**（不碰网关、IP、路由，只调地址选择优先级）：

```bash
# /etc/gai.conf（文件原本不存在，新建即可）
precedence ::ffff:0:0/96  100     # 让 IPv4 映射地址优先级最高
```

验证：`curl` 不再需要 `-4`，直接返回 200；`pip install` 正常。

> 💡 **运维知识点**：「能 ping 通网关、路由也正常，但访问外网报网络不可达」
> 时，先试 `curl -4`。这是 IPv6 优先造成的经典陷阱，尤其在只有 IPv4 出口的内网里。

### 10.4 缺陷修复①：Chroma 集成从来没能真正跑通

**这是本次最有价值的发现。**

装上 chromadb 后，`VECTOR_BACKEND=auto` 自动切到 Chroma，结果立刻报错：

```
ValueError: Expected each embedding in the embeddings to be a list, got ['dict']
```

**根因**：

| 事实 | 说明 |
|---|---|
| `SimpleEmbedder` 产出**稀疏 dict** | `{'connection': 1, 'refused': 1, '连': 1, ...}` |
| Chroma 只接受**稠密 float 列表** | 类型不兼容 |
| **为什么一直没暴露？** | 因为 chromadb 从来没装成功过，`auto` 永远降级到内存向量库（它的 `cosine_similarity` 同时支持 dict 和 list） |

**典型的「代码路径从未被执行过」的隐藏 bug** —— 只有在真正装上向量库那一刻才现形。

**修复方案：特征哈希（hashing trick）**

在 `src/rag.py` 新增 `to_dense()`，把稀疏词频折叠成固定维度的稠密向量，
并在 `ChromaStore.add()` / `search()` 里统一转换。

**第一次尝试失败**：单纯累加（1024 维）导致哈希冲突「凭空制造相似度」，
8 个查询里有 **2 个 Top-1 被挤错**（例如 `Too many connections` 被检索成
`Too many open files` —— 明显错误）。

**最终方案：带符号哈希 + 4096 维**
用哈希的另一个位决定正负号，让冲突项正负相消（期望为 0）。

**效果验证**（8 个真实查询对比稀疏版与稠密版的 Top-1）：

```
=== Top-1 一致率：8/8 (100%) ===
  ✓ MISCONF Redis...        → redis-errors.md · MISCONF RDB 持久化失败
  ✓ java.lang.OutOfMemoryError → tomcat-errors.md · Java heap space
  ✓ Connection refused      → nginx-errors.md · 502 Bad Gateway
  ✓ No space left on device → mysql-errors.md · 磁盘满
  ✓ Too many connections    → mysql-errors.md · 连接数耗尽
  ✓ KeyError                → python-app-errors.md · KeyError
  ✓ Permission denied .rdb  → redis-errors.md · MISCONF
  ✓ Deadlock found          → mysql-errors.md · 死锁
```

**结果**：向量库后端成功切到 **chroma** 并落盘持久化
（`data/chroma/chroma.sqlite3`），51 个片段检索正常，14 个测试全过。

### 10.5 缺陷修复②：「静默降级」把假数据写进了真实库

**问题**：`POST /api/scan` 在 Docker 中没有被监控容器时，会**静默使用演示样本**，
把编造的日志诊断结果写进真实数据库。跑完项目自带的冒烟测试后，库里就多了 3 条假数据：

```
=== 按 source 统计 ===
  file   33 条     ← 真实日志（/opt/logs）
  demo    3 条     ← 样本假数据！混进来了
```

**为什么危险**：面板看起来一切正常，内容却全是假的。这种「静默失败」
比直接报错危险得多 —— 你会在错误的信息上做判断。

**修复**：给采集链路加 `allow_demo` 开关

| 层 | 改动 |
|---|---|
| `collector.collect_all()` | 新增 `allow_demo: bool = True`；为 False 时不再兜底，采不到就返回空列表 |
| `pipeline.run_scan()` | 新增 `allow_demo` 参数透传；采到 0 条时返回 `note` 如实说明原因 |
| `api.py` 的 `POST /api/scan` | **固定传 `allow_demo=False`** —— 服务端永不注入假数据 |

**设计取舍**：本地命令行 `scan` 保留演示能力（不影响新手的「5 分钟跑通」体验），
但**服务端接口一律禁止**。想体验演示数据请用 `python -m src.main scan` 或 `/api/seed`
（后者来源明确标注为 `demo`）。

**验证**：

```
扫描前记录数: 33
扫描响应    : 未采集到日志（Docker 中没有被监控的容器），已跳过，未写入任何数据
扫描后记录数: 33
✓ 没有写入任何假数据
```
