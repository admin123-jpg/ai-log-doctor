## 二、12 个目录逐个说

### 🔹 `src/` — 核心代码（最重要）

11 个 Python 文件，共约 2700 行。这是整个项目的主体。

| 文件 | 行数 | 一句话职责 |
|---|---|---|
| `config.py` | 128 | **全局配置**：路径、环境变量、`TOP_K` 等常量。被几乎所有人 import |
| `collector.py` | 246 | **采集**：把日志读进来（Docker 日志 / 本地文件 / 目录批量） |
| `detector.py` | 219 | **检测**：用关键字 + 正则判断「有没有异常」，并切出异常片段 |
| `rag.py` | 450 | **检索**：知识库切片、向量化、算余弦相似度取 Top-3 |
| `llm.py` | 514 | **诊断**：拼 Prompt 调大模型（含无 Key 时的 Mock 规则库） |
| `db.py` | 301 | **存储**：SQLite 的增删改查，5 个函数对应 CRUD |
| `pipeline.py` | 152 | **编排**：把上面五步串成一条流水线，`analyze_text()` 是主入口 |
| `api.py` | 304 | **接口**：FastAPI 路由，`/docs` 可交互测试 |
| `main.py` | 345 | **命令行**：`check` / `kb` / `seed` / `scan` / `ingest` / `serve` 六个子命令 |
| `seed.py` | 101 | **造数据**：生成演示记录，让空数据库有话可说 |
| `__init__.py` | 12 | 包声明，声明版本号 |

**最该先看的两个**：`detector.py`（最简单，纯 Python）→ `pipeline.py`（只有 152 行，看懂它就懂了全项目）。

### 🔹 `knowledge/` — RAG 知识库（AI 回答的依据）

8 个 Markdown 手册，被切成 **51 个知识片段**。这是 RAG 检索的**资料来源**。

```
knowledge/
├── docker-errors.md          6 段   容器启动失败、OOM、端口占用
├── nginx-errors.md           6 段   502/504、权限、上游不可用
├── mysql-errors.md           6 段   连接拒绝、慢查询、死锁
├── ci-cd-errors.md           6 段   依赖安装失败、构建失败、测试超时
├── python-app-errors.md      6 段   Traceback、空指针、编码错误
├── redis-errors.md           6 段   MISCONF、fork 失败、主从断开
├── tomcat-errors.md          7 段   Java heap、连接池耗尽、文件句柄
└── middleware-errors.md      7 段   ES 磁盘只读、熔断、选举失败
```

每个 `##` 小节就是一个片段，结构统一：

```
## 错误标题
**现象**：日志长什么样
**常见原因**：为什么会这样
**排查步骤**：具体敲什么命令
**解决方案**：怎么修
```

> 💡 **想让它更聪明？加内容就行** —— 新增一个 `##` 小节，重启时自动进入知识库，**代码一行都不用改**。这就是 RAG 相对硬编码规则最大的优势。

程序分析的「原料」。因为这个项目要能在**没装 Docker 的电脑上跑通**，所以准备了本地样本兜底。

## 三、8 个顶层文件逐个说

| 文件 | 是什么 | 你会在什么时候关心它 |
|---|---|---|
| `README.md` | **项目说明书**（门面） | 第一份要看的文档；别人打开仓库也是先看它 |
| `requirements.txt` | **Python 依赖清单** | `pip install -r requirements.txt` 时 |
| `.env.example` | **环境变量模板** | 要配大模型 API Key 时，把它复制成 `.env` 再填 |
| `Dockerfile` | **打包说明书** | `docker build` 时；也是「层缓存优化」的典型场景 |
| `.dockerignore` | 打包时**排除**哪些文件 | 防止把 `venv/`、`data/` 打进镜像（否则镜像会巨大） |
| `docker-compose.yml` | **一键启动多个容器** | 想演示「真实容器日志」时：`docker compose up -d` |
| `nginx.conf` | Nginx 配置文件 | 被 `docker-compose.yml` 挂载进 nginx 容器；反向代理到 Flask |
| `.gitignore` | Git **忽略清单** | 决定哪些文件不进版本库（`venv/`、`data/`、`.env`、`__pycache__/`） |

**两个最容易混淆的**：

- `Dockerfile` vs `docker-compose.yml`
  → `Dockerfile` 是「**怎么做一个容器**」，`docker-compose.yml` 是「**怎么同时管好几个容器**」。
- `.env.example` vs `.env`
  → `.env.example` 是**模板**（会提交到 Git，给人看格式）；`.env` 是**你自己的真实配置**（不提交，含 Key）。

## 四、模块依赖关系：谁调用谁

这是我实测出来的 import 关系，箭头方向是「谁依赖谁」：

```
                    config.py
              （被 9 个模块依赖，最底层）
                        │
        ┌───────────────┼───────────────┬──────────────┐
        ↓               ↓               ↓              ↓
   collector.py    detector.py      rag.py         db.py
                        │               │
                        ↓               │
                    llm.py ←────────────┘
                        │
        ┌───────────────┘
        ↓
   pipeline.py  ← 编排层，把采集→检测→检索→诊断 串起来
        │
        ├────────────→ main.py     （命令行入口）
        ├────────────→ api.py      （HTTP 接口入口）
        └────────────→ seed.py     （造数据）

   scripts/ci_diagnose.py ──→ pipeline.py   （CI 侧复用同一条链路）
```

**三条重要规律**：

1. **`config.py` 是根基** —— 被 9 个模块依赖，但它自己不依赖任何内部模块。所有路径、常量都从这取，改配置只改一处。
2. **`pipeline.py` 是唯一的编排层** —— 命令行、HTTP 接口、CI 脚本**三个入口都调它**。这意味着你加一个新入口时不用重写流程。
3. **`detector.py` 里有一处特殊的局部导入** —— 第 190 行 `from .llm import MOCK_RULES` 写在函数内部而非文件顶部。这是为了避免「检测」和「诊断」两个模块互相循环依赖，属于有意为之。

## 五、三种敏感度：哪些能动、哪些别碰

| 敏感度 | 文件 / 目录 | 说明 |
|---|---|---|
| 🟢 **放心改** | `knowledge/*.md` | 加排错经验。改完重启服务即可生效，代码零改动 |
| 🟢 **放心改** | `samples/app-logs/*.log` | 换成你自己的日志，然后 `ingest --dir` |
| 🟢 **放心改** | `web/index.html` | 改前端样式、加字段，纯静态文件 |
| 🟢 **放心删** | `data/`、`.pytest_cache/` | 删了会重新生成（`data/` 删后要重跑 seed） |
| 🟡 **谨慎改** | `src/llm.py` 的 `MOCK_RULES` | 加诊断规则时**顺序很重要**：具体规则必须排在泛化规则前面（`OutOfMemoryError` 含 `MemoryError`，顺序错了会误判） |
| 🟡 **谨慎改** | `src/detector.py` 的切分逻辑 | 改动会直接影响「一条日志能切出几个异常」，务必重跑 `ingest` 对比结果 |
| 🟡 **谨慎改** | `requirements.txt` | 加依赖后要重新 `pip install` |
| 🔴 **别动** | `venv/` | 虚拟环境，损坏就重建，不要手动改里面 |
| 🔴 **别动** | `src/config.py` 的路径常量 | 改了会导致找不到知识库 / 数据库 |
| 🔴 **绝不提交** | `.env` | 含 API Key。已在 `.gitignore` 里，别把它推上 GitHub |

## 七、改成你自己的项目，只需要动这几处

如果要把这个项目改造成「你自己的日志分析工具」，按这个顺序动，改动量最小：

| 步骤 | 改哪里 | 具体做什么 |
|---|---|---|
| 1 | `knowledge/` | 换成你自己领域的排错手册（格式照抄现有的四个小标题） |
| 2 | `samples/app-logs/` | 换成你自己的日志文件 |
| 3 | `src/config.py` | 改关键词列表、`TOP_K`、端口 |
| 4 | `src/llm.py` | 补你自己的 `MOCK_RULES` 规则；接真模型时改 Prompt 模板 |
| 5 | `.env` | 填你自己的 API Key |
| 6 | `README.md` | 改项目名、改架构图说明 |

**不用动的**：`api.py`、`db.py`、`collector.py`、`web/index.html`、`main.py` —— 这些是通用管道，与业务无关。**这正是分层设计的意义。**

## 八、常见疑问

**Q：为什么左边还看到 `__pycache__` 之类的东西？**
A：Python 运行 `.py` 时会生成 `__pycache__/` 存放字节码缓存，加速下次启动。VS Code 默认隐藏它，`.gitignore` 也排除它，**不用管**。

**Q：`venv/` 有好几百 MB，能删吗？**
A：能删，但删了就得重建：
```bash
python -m venv venv
venv\Scripts\python.exe -m pip install -r requirements.txt
```
不建议随手删 —— 重建要等几分钟。

**Q：我可以把这个目录复制一份改着玩吗？**
A：**非常推荐**。复制一份改名（比如 `ai-log-doctor-copy`），在里面随便改。原版留着当参考，改坏了也不心疼。

**Q：项目根目录到底在哪？**
A：
```
C:\Users\ss\WorkBuddy\2026-09-15-00-46-43\ai-log-doctor
```
注意 `ai-log-doctor` 里面还有 `.git`（如果初始化过），**用 VS Code 打开时要打开 `ai-log-doctor` 这一层**，不要打开它的上一层，否则资源管理器里会多出无关目录。

**Q：怎么一眼看出哪些文件是自动生成的？**
A：看 `.gitignore`。里面列出的路径（`venv/`、`data/`、`__pycache__/`、`.pytest_cache/`、`.env`）都是**自动生成或不该提交的**。剩下的才是真正需要你维护的文件。

## 附录 A：`@` 是什么 —— 装饰器

> 读代码时最常见的第一道坎。看到 `@dataclass`、`@app.get(...)` 不知道什么意思，看这一节就够了。

### 一句话

`@` 是一个**动作标记**，含义是：**把下面这个东西，交给 `@` 后面那个名字去处理一下。**

### 本质：它就是一句话的简写

```python
@deco
def f(): ...
```

**完全等价于**：

```python
def f(): ...
f = deco(f)          # ← @ 的全部含义就在这一行
```

所以 `@` 一点都不神秘，把它读成「**f 等于 deco(f)**」就对了。

**实测验证**（本项目 venv 实跑，三段结果一致）：

```
① 不加 @ 时传参数   → A() takes no arguments      ← 裸类，不接受参数
② 手动装饰后        → A(x=1, y='a')               ← A = dataclass(A)
③ 用 @dataclass     → B(x=1, y='a')               ← 和 ② 一模一样

   @dataclass   ≡   B = dataclass(B)
```

② 和 ③ 结果完全相同，证明 `@` 只是语法糖，没有额外魔法。

### 为什么能这么写

因为 Python 里**函数和类都是普通对象**，可以像数字、字符串一样当参数传给别的函数、当返回值返回。

装饰器函数做的事就是三步：**收到一个函数/类 → 加工 → 把它（或增强版）还回来**。

### 自己造一个装饰器

```python
def log_time(func):                    # ① 收到一个函数
    def wrapper(*args, **kwargs):      # ② 把原函数包一层
        print(f"→ 开始执行 {func.__name__}()")
        result = func(*args, **kwargs) # ③ 中间照常执行原函数
        print(f"→ {func.__name__}() 执行完毕")
        return result
    return wrapper                     # ④ 返回包装后的函数


@log_time
def scan_logs():
    print("   （正在扫描日志...）")
    return 42
```

实测运行 `scan_logs()` 的输出：

```
→ 开始执行 scan_logs()
   （正在扫描日志...）
→ scan_logs() 执行完毕
```

**注意函数体里一行打印都没写** —— 上下两行是装饰器加的。这就是「装饰」的字面意思：**不修改原函数，在外面套一层。**

### ⭐ 最关键的一句：`@` 本身不干活，干活的是它后面的名字

同一个符号，后面跟不同名字，作用天差地别。本项目一共用了 **5 种**：

| 写法 | 出现位置 | 谁在干活 | 干什么 |
|---|---|---|---|
| `@dataclass` | 3 处 | 内置 `dataclasses` | 给类自动补 `__init__` / `__repr__` / `__eq__` |
| `@app.get("/api/...")` | **14 处** | FastAPI | 把函数注册成 HTTP 路由（所以 `/docs` 里能看到） |
| `@classmethod` | `config.py` 2 处 | Python 内置 | 让方法能用类名调用，不用先创建实例 |
| `@asynccontextmanager` | `api.py:46` | `contextlib` | 让生成器函数支持 `async with` |
| `@pytest.fixture(autouse=True)` | `tests/test_basic.py:27` | pytest | 标记为「测试前自动执行」的夹具 |

一句话概括：`api.py` 里那 14 个 `@app.get` / `@app.post`，全是在给函数**加"能被网址访问"的能力**。函数本身还是普通 Python 函数，`@` 只是把它接到网络上了。

### 新手必踩的坑：带括号 vs 不带括号

```python
@dataclass                  # 不带括号
class A: ...

@app.get("/api/health")     # 带括号  ← 完全不同的机制
def health(): ...
```

```python
# 不带括号：deco 本身就是装饰器
A = dataclass(A)

# 带括号：先"造"一个装饰器出来，再套上去（两层调用）
health = app.get("/api/health")(health)
```

带括号的这叫**装饰器工厂**：`app.get("/api/health")` 先产出一个「专门用来注册 `/api/health` 这个路径」的装饰器，再套到 `health` 函数上。

**括号里写的是配置参数（路径、HTTP 方法、标签），不是函数的参数。** 这是最容易看错的地方 —— 很多人以为 `@app.get("/api/health")` 是在给 `health()` 传参，不是的。

> **读法技巧**：看到 `@` 先数括号。有括号 → 先配置，再装饰。

### 看代码时的三秒钟判断法

遇到任何 `@xxx`，问自己三句话：

1. **后面有括号吗？** 有 → 先配置再装饰。
2. **`xxx` 是谁提供的？** `dataclasses` / `fastapi` / `pytest` / Python 内置 → 查它的文档。
3. **它在给下面这个函数/类加什么能力？** ← 最重要的一问。

### 你什么时候会自己写装饰器？

**新手阶段基本不用写。** 但有一个信号出现了就该考虑用：

> 如果你发现自己把同一段代码复制到第 3 个函数里了。

比如想让每个扫描函数都自动打印耗时、自动记一条日志 —— 与其在 5 个函数里各复制一遍，不如写一个装饰器套上去。

**装饰器存在的唯一理由**：给多个函数加同样的「前后处理」，而不污染函数本身。

## 附录 B：`@dataclass` 是什么

> 本项目 `collector.py`、`detector.py`、`rag.py` 里各用了一次，是最值得先掌握的语法糖。

### 一句话

`@dataclass` 是一个**「帮你自动写样板代码」的装饰器**。

### 不用它，你得写多少

同一个类，两种写法**完全等价**：

```python
# 手写版：12 行
class Detection:
    def __init__(self, hit, keyword="", severity="medium", snippet=""):
        self.hit = hit
        self.keyword = keyword
        self.severity = severity
        self.snippet = snippet

    def __repr__(self):
        return f"Detection(hit={self.hit!r}, keyword={self.keyword!r}, ...)"

    def __eq__(self, other):
        return (self.hit, self.keyword, self.severity, self.snippet) == \
               (other.hit, other.keyword, other.severity, other.snippet)
```

```python
# @dataclass 版：5 行，效果一模一样
@dataclass
class Detection:
    hit: bool                 # 是否命中异常
    keyword: str = ""         # 命中的关键字
    severity: str = "medium"  # 严重程度
    snippet: str = ""         # 异常上下文
```

省掉的代码有个共同点：**又长又没信息量**（全是 `self.x = x` 这种机械重复）。dataclass 就是把这种重复交给 Python 去做。

### 它自动生成的三个方法

**实测输出**（用项目里的 `Detection` 真跑）：

| 方法 | 作用 | 实测结果 |
|---|---|---|
| `__init__` | 能直接传参构造 | `Detection(hit=True, keyword='Out of memory', severity='medium', snippet='')` |
| `__repr__` | `print` 出来人能看懂 | 没写的话只显示 `<object at 0x0000021A...>`，调试等于瞎子 |
| `__eq__` | 两个对象能直接 `==` 比内容 | 内容相同 → `True`；内容不同 → `False` |

关于 `__eq__` 要特别说明：**不写它的话，`==` 比的是「是不是同一个对象」（内存地址）**，即使两个对象内容完全一样也返回 `False`。这是新手很容易踩的坑。

构造完之后它还是个普通对象，字段可读可改：

```python
d.severity = "high"      # 正常赋值，没问题
```

### 语法规则就两条

**规则 1**：字段写法是 `名字: 类型`，**不写 `self.`**

```python
@dataclass
class Detection:
    hit: bool                 # 没默认值 → 必须传
    keyword: str = ""         # 有默认值 → 可以不传
```

**规则 2**：**有默认值的字段必须排在没默认值的后面**，否则直接报错

```python
@dataclass
class Bad:
    a: str = ""     # 有默认值
    b: str          # 没默认值
# TypeError: non-default argument 'b' follows default argument
```

这条规则很合理 —— 和函数参数的「必填在前、可选在后」是一个道理。

### 项目里用了 3 处，都是同一个角色

| 位置 | 类名 | 装什么东西 |
|---|---|---|
| `collector.py:26` | `LogItem` | 一条日志：来源 / 服务名 / 正文 |
| `detector.py:19` | `Detection` | 一次检测结果：是否命中 / 关键字 / 严重度 / 上下文 |
| `rag.py:34` | `Chunk` | 一个知识片段：ID / 来源文件 / 标题 / 正文 |

共同点：**都是「把几个字段打包在一起传递」的容器**，本身没有任何业务逻辑。

这正是 dataclass 的最佳使用场景 —— **有字段、没行为**。

### 顺便解开一个疑惑：为什么 `api.py` 用的是 Pydantic？

`api.py` 里的请求模型**没有**用 dataclass：

```python
from pydantic import BaseModel, Field

class DiagnosisUpdate(BaseModel):     # 注意这里是 BaseModel
    status: str | None = None
```

同一个项目里两种都用，是因为职责不同：

| | `@dataclass` | Pydantic `BaseModel` |
|---|---|---|
| **干什么** | 省样板代码（**写起来快**） | 校验数据（**防错**） |
| **传错类型** | 不管，照收 | 返回 400 错误并说明原因 |
| **用在哪** | 项目**内部**函数之间传数据 | **接口边界**（外部传进来的数据） |

**原则：内部传数据用 dataclass（轻、无依赖）；外部输入用 Pydantic（会校验、更安全）。**

因为 `LogItem`、`Chunk` 都是自己代码造出来的，不会错；而 HTTP 请求是别人发来的，必须防。

### 两个以后会用到的扩展

```python
@dataclass(frozen=True)        # 不可变版本，改字段会报错（适合当"配置"用）
class Settings:
    port: int = 8000


# 字段是 list/dict 时，不能写 = []（Python 3.11+ 会直接报错禁止；
# 更早的版本更危险 —— 所有实例会共享同一个列表）
from dataclasses import field

@dataclass
class Report:
    items: list = field(default_factory=list)   # 每次都新建一个空列表
```

> 📌 小提示：如果你要写 `field(default_factory=...)`，记得在文件顶部补上 `from dataclasses import field`。反过来，**引入了但没用到的导入不会报错，只会让代码变脏** —— VS Code 会把它显示成灰色并标 `Unnecessary import`，看到就顺手删掉。
